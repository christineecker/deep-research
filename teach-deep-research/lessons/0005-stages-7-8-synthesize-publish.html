Lesson 5 of the deep-research course

Stages 7–8: the bottom line, and which file to open

The pipeline's last stretch turns extracted, appraised papers into something you can actually read. This lesson covers the rules that keep that read honest, and which of the three output files answers which question.

Stage 7 — Synthesize

Main thread only — no subagent writes the synthesis. The core moves: tabulate effect direction per outcome (not pooled effects — recall from Lesson 1, this is not a meta-analysis), surface agreement and conflict with an explanation of why studies disagree, rate certainty, name the gaps, and keep a hard-walled hypotheses section. Three invariants are what make that trustworthy rather than just tidy:

  • Null and negative findings are actively searched for — screening must not exclude on outcome positivity, so a synthesis can't quietly become a highlight reel.
  • Conflicts are never averaged away. Two studies disagreeing is a finding to explain, not noise to smooth over.
  • "New insights / hypotheses" is hard-walled from "what the evidence shows." If the report speculates, it says so in a clearly separated section — it never blends a guess into the evidence tabulation.

Read outputs/report.md with those three in mind and you're reading it the way the skill intends: check the gaps section as seriously as the findings, and treat the hypotheses section as "worth investigating," not "established."

Stage 7b — Digest

One opus subagent compresses the finished report into outputs/digest.md: an answer-first paragraph, a categorical outcomes table (outcome / direction / certainty / studies), and an ## Open Questions section merging gaps and hypotheses, each paired with what would resolve it. No new research happens here, no re-derived judgement — same GRADE wording, same hard wall between evidence and speculation as the source report. In wiki mode this digest becomes the actual page content at research/reviews/<slug>.md; the full report stays linked as the audit trail behind it.

Stage 8 — Assemble, verify, publish

Fixed order, every time: 

assemble.py run  ->  verify.py run  ->  render.py / html_report.py  ->  okf.py promote --check  ->  okf.py promote

assemble.py decides which artifacts are admissible and writes outputs/result.json. verify.py runs 12 report checks plus 4 evidence-kernel checks and writes outputs/verification.json — this is the file that answers "did this run pass its own sanity checks," independent of whether you agree with its conclusions. okf.py promote (wiki mode only) is the step that actually publishes into the wiki, and it blocks if Stage 7b hasn't produced a completed digest or if verification failed. In standalone repo mode there's no promote step at all — outputs/report.md/digest.md plus the project's manuscript.qmd/refs.bib under projects/<slug>/ are the deliverable.

One nuance worth knowing: the evidence-kernel gate is off by default until a live end-to-end run has passed once. Gate off, those kernel checks still run and still show up in verification.json — they just warn instead of blocking. A hash-mismatched snapshot or a quote that doesn't match its source span is never silently downgraded, though — tamper detection stays a hard failure regardless of the gate setting.

The tangible win for this lesson: handed a finished run directory, you know exactly which file to open for "give me the bottom line" versus "show me the full audit trail" versus "did this actually pass its checks" — and you can explain why a report's hypotheses section is never itself a citable finding.
