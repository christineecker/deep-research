# Reference manager v2 — plan (backlog)

This document is a forward-looking backlog, not a build log. Completed work
is described only briefly, with pointers to the actual code/tests as the
source of truth — read those, not this file, for how something works.
Historical design rationale that's no longer load-bearing has been dropped;
`REFERENCE_MANAGER_V2_ADR.md` has been folded in here and removed.

## What this project is

A reliable local SQLite backend for papers, identifiers, assets,
attachments, organization, and citations — serving deep-research's own
automation (dedup, evidence-linking, citation keys, search) — plus a
`/deep-research:export readcube` command that prepares ReadCube-compatible
import bundles (RIS + PDFs) on request. **ReadCube itself is the human
library UI and PDF/figure viewer; this project does not build or maintain
either.** A custom browser library table, an embedded PDF reader, in-app
highlight/figure-capture UI, and any local HTTP service exposing them are
permanently out of scope, not just deferred. If a narrow agent-driven need
for page/figure inspection ever arises, it should be a CLI/script
capability against the existing poppler/tesseract tooling — not a browser
feature.

## What exists today

- **`skills/deep-research/scripts/refmgr/`** — SQLite storage/service
  layer: migrations, identity normalization (DOI/PMID/PMCID/URL),
  repositories (papers, identifiers, assets, attachments, organization,
  audit, merges, search, saved_searches), `service.py` facade. Wired into
  `registry.py`'s `add-pdf`/`import-folder` (and `paper.py`'s `--pdf`
  ingestion, same code path) for PDF attachment storage; bibliographic
  metadata still lives in `registry.jsonl` only — see "Open decisions".
- **Extraction/snapshot ↔ refmgr attachment linkage**: snapshot schema
  (§10) `asset` supports a refmgr-backed shape alongside the legacy
  wiki-relative one; `store.py` freshness checks and `okf.py`'s wiki-mode
  tamper check handle both; `source.py local --repo --attachment-id`
  ingests a PDF already staged via `registry.py add-pdf`.
- **`export.py`** (`readcube` subcommand) + `export_select.py`,
  `export_select_refmgr.py`, `ris.py`, `export_ledger.py` — selection, two
  `AssetSource` implementations (`--source legacy|refmgr`), RIS/BibTeX
  serialization, staged atomic publish, incremental export ledger,
  per-record fulltext-status reporting in `import-report.md`. Docs:
  `commands/export.md`, `references/readcube-export.md`,
  `references/schema/17-export-manifest.md`.
- **Search**: `refmgr/repositories/search.py` (FTS5) + `saved_searches.py`,
  wired into `service.py` as `.search`/`.saved_searches`.
- **`okf-export`** (`research.py`) promotes hand-picked registry papers
  into an OKF wiki bundle without a blanket `--force`; only the two
  pipeline-shaped checks that don't apply to a registry selection
  (`C-SEARCH-LOG`, `C-PRISMA`) are exempted via `okf.py promote
  --exempt-check`.
- **Personal annotations vs verified claims**: paper-summary output has a
  distinct, clearly-labeled "Personal notes (unverified)" section fed from
  `annotations.jsonl`, never mixed with extraction-derived claims.
- **Backup/restore and extended health checks**: `scripts/backup.py`
  (`create`/`verify`/`restore`) and the additional `refmgr/doctor.py`
  checks described under "Phase 6" below.
- **10k/100k retrieval benchmark**: `scripts/benchmark_refmgr.py` and
  `BENCHMARK_RESULTS.md` at the repo root — see "Phase 4" below.
- **Compatibility-trial fixture** for the one remaining manual Phase 2
  step: `skills/deep-research/references/fixtures/compat-trial/` — a real
  bundle generated by the actual CLI, with a README walking through what
  to check in the ReadCube desktop app.

All of the above has its own test suite (`skills/deep-research/tests/
test_refmgr*.py`, `test_export*.py`, `test_registry.py`, `test_paper.py`,
`test_source.py`, `test_okf*.py`, `test_ris.py`) and is not further
described here.

The pre-existing, separately-shipped JSONL prototype
(`annotations.py`/`embeddings.py`/`registry.py search`) is real, tested,
documented, user-facing functionality — untouched by this plan and not
being removed. It predates and is independent of the `refmgr` work above;
see "Known issues and standing decisions" for its specific gaps relative
to the `refmgr` data model.

## Data model and invariants

Implemented entities: Paper, Identifier, Asset, Attachment, Organization,
Audit/merge — immutable IDs, identifier normalization with alias
retention, content-addressed dedup, attachments never overwritten,
original PDFs immutable, visible diagnostics over silent failure. Search
(FTS5) is a rebuildable derived index, never a source of truth.

Deferred, open question (see "Open decisions"): Page-derivative,
Annotation, and Job entities. Embedding rework (real input hashes and
config fingerprints, chunk-level granularity, replacing
`embeddings.py`'s model-name-only freshness check) is paused along with
the rest of Phase 4 — see below.

## Known issues and standing decisions

- **Interpreter**: target the uv-managed 3.11.15 environment (what `pip`
  resolves to on this machine), not whichever `python3` happens to be on
  PATH — the existing `sentence-transformers` carve-out already assumes
  this. The full test suite runs clean under it.
- **Storage**: SQLite (stdlib) + FTS5 — confirmed available, no install
  needed, WAL-safe on this filesystem.
- **PDF/OCR**: `pdftoppm`/`pdftotext`/`tesseract` CLI tools are available
  and sufficient for now; only add `pymupdf`/`pdf2image`/`pytesseract`
  Python bindings when a concrete task needs in-process page access that
  shelling out can't do cleanly — don't install them speculatively.
- **Dependency policy**: core deep-research skill scripts remain
  stdlib-only. `sentence-transformers` is the one existing, documented
  exception (`references/acquisition.md`). No FastAPI/uvicorn or frontend
  build tooling is needed — the browser-app direction that would have
  required them is retired.
- **`Registry` read-modify-write race — fixed**: `Registry.locked()` now
  re-reads the store from disk *inside* `advisory_lock`, and every
  mutating call site goes through it rather than taking the lock
  directly (`registry.py`, `Registry.locked`). `refmgr`'s own
  `db.transaction` was never affected by this.
- **Disposition of the JSONL prototype**: `annotations.py`'s Annotation
  model is paper-level only (tags/rating/note) — no attachment anchoring,
  bounding boxes, or revision history. `embeddings.py`'s Embedding model
  has no chunk granularity, input hash, or processor version — can't
  safely detect staleness or mixed-model comparisons. None of this is
  being deleted or rewritten now — it's real working code — but none of
  it should be treated as a model to extend when building the items
  below.

## Remaining work

### Phase 2 close-out (manual, needs the user)

- **ReadCube compatibility trial**: import
  `skills/deep-research/references/fixtures/compat-trial/bundle-dest/compat-trial-*/`
  into the real ReadCube desktop app and work through that directory's
  README (RIS field preservation, PDF matching, supplement/version
  association, repeated-import behavior, figure viewing). Record the app
  version and what you observe.
- **iCloud destination acceptance**: once given a real destination folder,
  publish a real batch there and verify against the compatibility trial's
  findings.

### Phase 4 — paused, not active backlog

Lexical search (FTS5) and saved searches already shipped (see "What
exists today") and are not being removed. The 10k/100k-record latency
benchmark is also now done — see `BENCHMARK_RESULTS.md` at the repo root
(deterministic synthetic fixtures, `scripts/benchmark_refmgr.py`) — and
found and fixed a real O(n²) `SearchRepository.rebuild()` cost along the
way. Still paused, not scheduled: the embeddings rework (input hashes,
config fingerprints, chunk granularity), the exact-vs-ANN retrieval
benchmark, attachment/processing/page-level-text filters, and bounded
OCR/extraction/indexing workers. Restore any of these as their own
section here when picked back up rather than assuming the prior scoping
still applies unchanged.

### Phase 5 — done

PDF attachment routing, extraction/snapshot ↔ attachment linkage,
annotations-vs-verified-claims separation, and the okf-export exemption
mechanism are all shipped — see "What exists today" above for pointers.
Citation-key collision handling was already implemented and tested in
`refmgr`'s `PaperRepository.set_citation_key`.

Not audited as part of this: `verify.py`'s own kernel checks were
exercised incidentally through the attachment-linkage work but not
reviewed end-to-end for every other refmgr-adjacent code path — treat
"the two known asset-consumers fixed" as the actual scope, not "every
consumer of `snapshot.asset` is now refmgr-aware."

### Phase 6 — recovery, release, and scale hardening

Mostly shipped: `scripts/backup.py` (`create`/`verify`/`restore`) covers
SQLite backup via the online backup API with an asset/file manifest and
checksums, coordinated-lock consistency across the registry/refmgr/
annotations/embeddings/export-ledger stores, and restore into a fresh
directory followed by a deep `refmgr doctor` pass — exercised end to end
against a fixture with attachments, figures, a merge, an annotation, and a
collection (`tests/test_backup.py`). `refmgr/doctor.py` gained SQLite
integrity/foreign-key checks, figure-ownership and identifier-primary
consistency checks, chunk-staleness reporting, and untracked-asset-file
detection on top of its existing missing/corrupt-asset and orphan checks.

Still open: retention/cleanup controls (nothing prunes old backups or
orphaned assets automatically — `doctor` only reports them) and bounded
caches/workers (no scope here needed one yet). A documented acceptance
walkthrough beyond the test suite itself has not been written.

## Open decisions

1. **CLI cutover timing**: PDF attachment storage (`add-pdf`/
   `import-folder`) is cut over (Phase 5). Bibliographic
   metadata/lifecycle (`add`/`import-bib`/`lookup`/`list`/`search`/
   `promote`/`appraise-promote`) still lives in `registry.jsonl` only —
   whether/when to route that through `refmgr`'s `papers`/`identifiers`
   tables too remains open. Not required for anything currently
   buildable — the export command targets the legacy registry directly
   and `RefmgrAssetSource` only needs `refmgr` data to exist, not
   `registry.py` writing all of it.
2. **Whether Page-derivative/Annotation/Job entities are still needed at
   all**, now that ReadCube owns PDF viewing/annotation. Recommendation:
   don't build them speculatively — revisit only if a concrete
   agent-driven use case requires it, and scope it as a narrow CLI
   capability, not a UI feature, per "What this project is" above.
3. Backup destination remains user-configured, no cloud sync — otherwise
   unchanged from earlier defaults.
