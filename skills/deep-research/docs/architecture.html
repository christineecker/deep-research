Standalone mode

Two storage roots, not one migration. Either works end to end without the other.

A run can live under a wiki root (the legacy path, with a wiki-level paper pool) or under a repo root (self-contained, with a canonical registry). wiki-manager is never a runtime dependency of the repo path. The wiki bridges in both directions exist for interoperability and are never a required step.

Paper store<wiki>/assets/papers/pool.jsonl<repo>/data/papers/registry.jsonl
Intake + PDF indexlibrary.py --wikiregistry.py --repo (add-pdf, import-folder)

--wiki and --repo are mutually exclusive per invocation, not per script — most commands accept either. Everything about the pipeline's shape is identical between them; only the root and which script handles pool/PDF intake differ.

Layout

Exactly what research.py init <path> creates, plus the directories that appear on first use. Sketch first, exact tree below it:

projects/, runs/, and exports/ — three different jobs

These three sit at the same level and are easy to lump together as "output," but they hold fundamentally different things: one is the deliverable you're writing, one is scratch state from getting there, and one is a reserved landing spot nothing currently uses.

One paper's worth of registry data (its extraction, its appraisal) can be produced by any number of runs over time — a review, a one-paper summary, an extract-only call — and each promotes into the same data/papers/ store. A project, by contrast, is the one write-up for one question: its manuscript.qmd is not derived from anything and is not reproduced by re-running a command. exports/ looks like it should be the third leg of that story (rendered deliverables) but isn't yet — every rendering path that exists today (render.py, html_report.py, ReadCube's export, bib-export) writes to a run's own outputs/, or to an explicit --out/--destination path you name, never into this scaffolded folder automatically.

Why data/sources/ looks like a run directory. It is one, deliberately. Every write-once/hash/verify function in store.py is a pure function of a run-directory-shaped path, so the global store is just data/sources passed in as that path — zero duplication and zero risk to the audited evidence-kernel code. Snapshots are written to snapshots/; global reads fall back to the legacy sources/ dirname for repos written before that rename, and writes never use it.
runs/ detail beyond this page. The full Stage 0-8 shape (workspace/search/, screening/<screener>/, PRISMA, taskboard mechanics) is documented in full in Full pipeline. The lightweight single-paper-summary/paper-summary-set shape — same runs/ root, far fewer files — is documented in Paper summaries. This page only distinguishes the directory's role from its siblings; it does not re-document either shape's stage-by-stage behavior.

Source Of Truth vs. Derived

Knowing which is which tells you what a backup must contain and what a corruption costs you.

FileStatusIf lost
data/papers/registry.jsonlSource of truthUnrecoverable. This is the library
data/sources/snapshots/, events.jsonlSource of truthUnrecoverable; every span stops verifying
data/papers/extractions/, appraisals/Source of truthUnrecoverable; re-extraction means re-running subagents
data/refmgr/assets/ (PDF bytes)Source of truthUnrecoverable from the registry — restore from backup or re-import
data/papers/annotations.jsonlSource of truth (your opinions)Unrecoverable

data/papers/pool.jsonlDerivedregistry.py pool
papers_fts, chunks_fts, paper_termsDerivedregistry.py reindex

A lost or corrupt SQLite database is repaired, not restored. If the index is missing or unusable, search --q falls back to scanning snapshot bodies — slower, same answers.

The Reuse Loop

This is the point of the whole storage model: work done once for any question is available to every later question that touches the same paper.

Stage 2   pool.py seed    --run-dir <run> --repo <path> --query "..."
          →  scores the registry against this run's question and upserts likely papers
             into corpus.jsonl as candidates (source: pool). They still get screened.

Stage 5   pool.py reuse   --run-dir <run> --repo <path> --pmid <pmid>
          →  matched: true + non-null extraction  ⇒  the canonical extraction is copied
             into workspace/extractions/, tagged "reused_from", and the subagent is skipped.

Stage 5   registry.py promote --repo <path> --run-dir <run>
exit      →  copies this run's fresh extractions into the canonical store and repoints
             the corpus record at them. Span-verified by default.

Stage 6   pool.py reuse ... --project <slug>      # same gate, now checking appraisal_path
Stage 6   registry.py appraise-promote --repo <path> --run-dir <run> --project <slug>
exit

Why repo mode needs no snapshot-carrying step

Store(run_dir, repo_root=<path>) writes new snapshots to the global store by default and falls back run-local → global on read. So a canonical extraction promoted from any run resolves its spans from any other run constructed with the same repo_root, byte-identically, with nothing to copy.

Wiki mode cannot do that — wiki runs have isolated per-run stores — so pool.py reuse there re-registers every snapshot a reused extraction's spans cite into the destination run's own store. Same source_id, content-addressed, so it resolves identically. Either way, a reused snapshot carries a register event rather than a fetch, so C-FRESH-FETCH correctly reports it as not retrieved in this run while C-SNAPSHOT and C-SPAN pass.

Appraisal Is Project-Scoped, On Purpose

The registry stores appraisals in a map keyed by project, not in a single field. Risk of bias and certainty are a function of the question a paper is being used to answer, not an intrinsic property of the paper.

"appraisals": {
  "adolescent-cbt":    "data/papers/appraisals/adolescent-cbt/pmid-12345678--cdi2-12wk.json",
  "digital-therapies": "data/papers/appraisals/digital-therapies/pmid-12345678--adherence.json"
}

Consequences worth knowing before they surprise you:

  • A lookup without --project never returns an appraisal.
  • The same paper can be appraised for one manuscript and not_appraised for another at the same moment, and both are correct.
  • Extractions are not project-scoped — a paper's data is its data. Only the judgement about it is scoped.

Commands

# repo / project lifecycle
python3 scripts/research.py init <path> [--from-wiki <wiki-root>]
python3 scripts/research.py project create <slug> --repo <path>
python3 scripts/research.py project list --repo <path>
python3 scripts/research.py export wiki --repo <path> --wiki <root> [--project <slug>]

# intake — all paths converge on Registry.register
python3 scripts/registry.py add           --repo <path> --pmid <pmid> | --doi <doi>
python3 scripts/registry.py add-pdf       --repo <path> --file <pdf> [--pmid/--doi/--pmcid/--title]
python3 scripts/registry.py import-bib    --repo <path> --file refs.bib
python3 scripts/registry.py import-folder --repo <path> --dir <folder> [--recursive]
python3 scripts/registry.py lookup        --repo <path> (--pmid|--doi|--pmcid|--evidence-id)
python3 scripts/registry.py list          --repo <path>
python3 scripts/registry.py pool          --repo <path>     # regenerate the derived view

# promotion
python3 scripts/registry.py promote          --repo <path> --run-dir <run>
python3 scripts/registry.py appraise-promote --repo <path> --run-dir <run> --project <slug>

# reuse
python3 scripts/pool.py seed   --run-dir <run> --repo <path> --query "..." [--include-metadata-only]
python3 scripts/pool.py lookup --repo <path> (--pmid|--doi|--pmcid) [--project <slug>]
python3 scripts/pool.py reuse  --run-dir <run> --repo <path> (--pmid|--doi|--pmcid) [--project <slug>]

# legacy bridge, one-way, never required
python3 scripts/pool.py migrate --from-wiki <wiki-root> --repo <path> [--project <slug>]

Migrating from a wiki pool

For every record in the legacy pool: register its bibliographic fields into the registry, then copy its freshest pointer that still resolves on disk for extraction and appraisal into the canonical store, carrying every snapshot those spans cite into the global source store so they keep verifying with no wiki involved. A pointer whose file has moved or vanished is reported under stale_pointers in the command's JSON — never silently dropped.

Who Else Reads This Store

There is no separate summary-only store and no separate reference-manager store. paper.py's summary profiles and the search/annotate/ask layer read and write the same registry, extractions, and appraisals the full pipeline does. A paper registered and extracted by a review is reused as-is by a later one-paper summary, and vice versa.

What Is Not Wired

  • SKILL.md's Stage 2–8 narrative still documents the wiki-backed path only. Running a project under a repo root today means using the research.py / registry.py commands directly rather than the stage prose.
  • status and screening on registry records are not set by any command. They exist for a project to use, not because anything writes them.
  • okf.py promote has no repo-mode equivalent. research.py export wiki is a plain file copy — a courtesy bundle, not a replacement for the validated promotion path.
  • --source refmgr in the ReadCube export cannot take --run-dir: a run's evidence ids use the registry's scheme, and there is no defined cross-resolution against refmgr identifiers yet.
